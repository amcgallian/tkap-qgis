Stratigraphic Phasing

Splits Stratigraphic Units into one layer per phase.

Overview

ActionWhat it does
Split by Phase…Builds the per-phase layers for one excavation field.
Plans from a Plan File…Builds one plan per Map Title: in a file of queries you wrote, then exports them.
Export Phase Plans…Exports one plan per phase using a print layout you designed.

The space_phase field holds a comma-separated list, one entry per space the SU belongs to:

Sp.85.3 (Abandonment), Sp.85.1 (Construction), Sp.85.2 (Occupation)

Each entry becomes a (space, phase) bucket, and each bucket becomes one output layer, e.g. Field6_Sp34_Phase1_Construction.

Grouping is per space, not per phase number. Phase numbers run independently within each space, so Sp.33.1 and Sp.34.1 are unrelated moments and stay in separate layers.

An SU can appear in several layers. One in several spaces lands in each space's layer, and one listed for several phases within a space (a wall built in one phase and still standing later) lands in every phase it lists. Geometry is duplicated across those layers, so the output feature count is higher than the input SU count.

Live filtered layers point at the same source with an editable filter, so nothing is copied. So Field6_Sp34_Phase1_Construction is really:

"area" = '6' AND "space_phase" LIKE '%Sp.34.1 (%'

Open Layer Properties → Source → Query Builder on any phase layer to add your own clauses. Because these address the same table as the source, they're locked read-only. Toggle Editing is disabled so an edit session can't reach production data. The filter stays editable; only the features are protected.

Temporary scratch layers are a frozen in-memory copy. Editable, because editing a copy can't reach the original. Gone when you close QGIS unless you save them.

GeoPackage writes every phase as a separate table in one .gpkg. The tool refuses to write to the source layer's own file.

Run

Output layers inherit the source layer's renderer, labelling, opacity and blend mode, so they look like what you started from. Turn that off with Inherit symbology from the source layer.

Tutorial: Plans from a Plan File

Split by Phase derives the plans from the data. A publication plan is often not that: 3.2.3 is a space-phase minus six SUs, and 3.5.1 is three spaces plus five loose SU numbers. Those decisions get made while writing up, so this reads them from a text file — one plan per Map Title:, with the query that defines it — builds a layer per plan, and hands them to Export Phase Plans.

------------------------------------------------------------
Hellenistic Pitting and Abandonment
------------------------------------------------------------

Map Title: 3.1 Hellenistic Pitting and Abandonment

Field3.1FeaturesPlan:
"field" = '3' AND "feature" IN ('117', '120', '125', '144')

Field3.1SUsPlan:
"area" = '3'
AND "sunumber" IN ('1819', '1820', '1823', '1847')
LineWhat it is
Map Title:Starts a plan. The rest of the line is the title, which becomes the layout's title and the file name.
…SUsPlan: / …FeaturesPlan: / …SpacesPlan:A query block. Only the ending matters — it says which layer to run the query against. The query goes on the line(s) under it and ends at a blank line.
------ rulesA section heading, for reading. Available as {section} in a title template.
# linesNotes, ignored. Comment out a plan rather than deleting a query you spent an afternoon getting right.

Queries are used exactly as written — they are the provider filter, the same thing you would type into Layer Properties → Source → Query Builder. Test one there, paste it here. A plan may have both blocks or only one.

Open it

Plugins → TKAP Tools → Plans from a Plan File… Don't have a file yet? Save a template to fill in… writes one with the format explained in it and two working example plans, and loads it so you can see it working before changing a word.

Spaces come free

You rarely write a …SpacesPlan: block. An SU query filtering on Sp.110.1 has already said its plan is about space 110, so the spaces are read back out of it and become the Spaces layer's filter:

3.2.1 mentions Sp.110.1 and Sp.111.1, so its space layer gets:
"space" IN ('110', '111')

Pick the Spaces layer and the space-number field — both guessed for you — and every plan that names a space gets one. In the Field 3 file that is 15 of the 16; 3.1 is a bare sunumber list, names no space, and correctly gets none. A written …SpacesPlan: block always wins over the derived one.

Spaces never go in the legend. They are context, not a subject of the plan, so each plan's space layer goes straight into the map frame and stays unchecked in the layer tree — which keeps an auto-updating legend from listing it.

Point it at your layers

The queries name their own columns, so the tool reads them and picks the SU and Features layers that fit — override either. Leave Features empty to build SU plans only.

Both layers are only ever read. A plan is always a separate layer; nothing filters, renames or edits the ones you point at.

Read the table

Every plan is listed with the number of SUs and features its queries actually select, checked against the layers you chose. A query that will not run says why — layer 'Features' has no attribute 'sunumber' tells you the two combo boxes are the wrong way round — and a plan selecting nothing is flagged in red before you export twenty of them.

Choose what a plan is

Both modes run the same query, so they select the same SUs either way. What differs is where an edit to a plan goes.

Copies are the default because reshaping a polygon for a figure is a normal thing to want and should not be able to touch the excavation record. Live mode is there for when you do mean the edit to land in the database — the dialog says so in red when it is selected.

Build and export

Each plan becomes a layer named after its title — 3.1 Hellenistic Pitting and Abandonment, verbatim, since layer names have no characters to sanitise away. File names still come out safe: 3.1_Hellenistic_Pitting_and_Abandonment.jpg.

They go into three groups — the SU plans, their features, their spaces — all taking the plan's name so Export Phase Plans pairs them automatically. The groups are stacked Spaces / Features / Plans, top to bottom, because space outlines read over the whole plan and a feature is cut into the SUs around it. The export forces that same order in the map frame, so it holds either way.

Build and Export… opens the export dialog on what it just built; Build layers only stops there.

Tutorial: Export Phase Plans

The tool doesn't invent a layout. Design one print layout in QGIS the way you want the plans to look, with north arrow, scale bar, legend and title block, and this walks the phase layers, showing one at a time, exporting a file for each.

Pick the group and the phases

Choose the group of phase layers and tick which ones to export.

Optionally pick a Features group

Features have no space_phase attribute, so they can't be split the way SUs are. Build the per-phase feature layers yourself, put them in a group, and point Features (optional) at it. Name each one after the phase layer it belongs with. Matching runs in this order:

OrderFor phase layer Field6_Sp34_Phase1_Construction
1. Same nameField6_Sp34_Phase1_Construction
2. Same name, any punctuation or casefield6 sp34 phase1 construction
3. Space and phase anywhere in the nameFeatures_Sp34_Phase1

Both the Sp and Phase numbers have to match. A phase with no features layer still exports, SUs only.

Pick your print layout

Set up the title, if you want one

Add a text item to your layout and type Title in it. That's the setup. The tool finds any label whose text is exactly that, rewrites it per phase, and puts Title back at the end. A label with the item id phase_title is always matched too.

Replace with: is a template. The default renders as Field 6 - Space 34, Phase 1 (Construction):

{field} - Space {space}, Phase {phase} ({phase_name})

Placeholders from a phase split: {field}, {space}, {phase}, {phase_name}. From a plan file: {title}, {number}, {name}, {section}, {spaces}. Either: {layer}, and for a line break.

Plan layers carry their own title, so the template for a plan set is just {title} — which is what the plan-file dialog sets when it hands over.

Choose what the map frame does

Map extent is one of three: leave it as set in the layout, zoom to each plan's own extent, or zoom once to all the selected plans together. The last is the one for a publication sequence — every plan comes out at the same scale and registration, so leafing through them shows the site changing rather than the frame moving. The map's own extent is put back when the run finishes.

Choose folder, format and DPI

JPEG by default. PNG, PDF and SVG also available.

Preview, then export

Preview… steps through the phases with Previous/Next, reporting the SU count and which features layer matched. It runs the same code path as the real export, so what you see is what gets written.

Output is one file per phase, named after the layer. Layer visibility, layer names, title text and legend state are all restored afterwards.

Output columns

Each output layer carries the source attributes plus three provenance columns, toggleable in the dialog. On live filtered layers these are virtual fields held in the QGIS project, so nothing is written to PostGIS.

ColumnMeaning
ph_spacespace number this layer represents
ph_numphase number within that space
ph_namephase name

Warnings

Non-fatal data problems show in the dialog and in Log Messages under the TKAP Phasing tab:

  • a space_phase with text the parser couldn't consume, usually a value truncated by a 254-character shapefile export. The parseable entries are still used;
  • a (space, phase) pair with conflicting phase names across SUs. The first-seen name is used;
  • an SU with no geometry.

SUs with a blank space_phase are counted as unphased and skipped.
